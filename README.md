# TaskForge API

A REST API for a task management app, built as a four-stage backend project. Started as a plain Express server with an in-memory array and ended up as a proper API with file-based persistence, async handling, and centralized error handling.

## What it does

Basic CRUD for tasks, plus a slightly unusual endpoint that simulates checking a task against a slow external service. Tasks live in a JSON file on disk, so restarting the server doesn't wipe your data.

## Stack

- Node.js + Express
- nanoid for generating task IDs
- fs/promises for reading and writing the data file
- No database — tasks.json is the "database"

## Getting started

```bash
git clone <your-repo-url>
cd TaskForge-API
npm install
npm start
```

The server runs on `http://localhost:3500` by default. Visit that URL in a browser to see a simple static page listing current tasks, or hit the API directly with Postman/Thunder Client.

## Task shape

```json
{
  "id": "string, generated by nanoid",
  "title": "string, required",
  "completed": "boolean, defaults to false",
  "createdAt": "ISO date string, set automatically"
}
```

## Endpoints

| Method | Route | Description |
|---|---|---|
| GET | `/api/tasks` | Get all tasks |
| GET | `/api/tasks/:id` | Get a single task |
| POST | `/api/tasks` | Create a task |
| PUT | `/api/tasks/:id` | Update a task (partial updates supported) |
| DELETE | `/api/tasks/:id` | Delete a task |
| GET | `/api/tasks/:id/verify` | Simulates a ~12s external check on a task |

### Status codes

| Situation | Code |
|---|---|
| Resource fetched successfully | 200 |
| Resource created successfully | 201 |
| Resource deleted successfully | 204 |
| Bad request body (e.g. missing title) | 400 |
| Resource not found | 404 |
| Task fails verification | 422 |
| Unexpected server error | 500 |

## Notable design decisions

**Data persistence.** Tasks are stored in `data/tasks.json` and read/written with `fs.promises` on every request. Not exactly a production-grade database, but it's enough to prove data survives a server restart, which was the point of this stage.

**The `/verify` endpoint.** This one artificially waits ~12 seconds before responding, wrapping `setTimeout` in a Promise so it can be awaited properly instead of nested in `.then()` callbacks. It's meant to simulate calling a slow third-party service. One seeded task is intentionally missing its `title` field, so this endpoint has something real to fail on — hitting `/verify` on that task returns a `422` instead of crashing the server.

**Error handling.** There's exactly one error-handling middleware, and it sits last in the stack. Every controller uses `try/catch` and calls `next(err)` rather than sending its own error response directly — including custom `AppError` instances for expected failures (like "task not found") and genuinely unexpected errors (like malformed JSON in the request body), which get caught and logged server-side without ever leaking a raw stack trace back to the client.

## Testing

Manually tested with Postman — a collection covering all six routes (success and failure cases for each) is included alongside this repo. To sanity check things yourself:

1. `npm start`
2. Hit `GET /api/tasks` to confirm the server's alive and seeded data loads
3. Create, update, and delete a task, confirming status codes match the table above
4. Try `/verify` on a valid task and on the seeded broken one
5. Send a POST with malformed JSON in the body — server should return a clean `400`, not crash

## Known limitations

- No authentication — anyone hitting the API can read/write any task
- `tasks.json` isn't safe for concurrent writes under real load; it's a learning-project stand-in for a proper database
- No pagination on `GET /api/tasks` — fine for a handful of tasks, not built for scale

Built as a four-stage backend project (routing → async → REST conventions & static files → centralized error handling)
